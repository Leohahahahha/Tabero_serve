## 1. Bash 多行粘贴触发 `free(): invalid pointer`

- **日期**：2026-09-02
- **状态**：已缓解，上游注入库仍需维护者修复。
- **现象**：在 VS Code 终端粘贴带反斜杠换行的命令时，Bash 直接 SIGABRT；单行命令正常。
- **排查过程**：先排除 Python、JAX 和 VS Code；在独立交互式 Bash 中用一条 `echo` 加换行即可稳定复现。分析 core dump 后，调用栈落在 `record_history_cmdline -> record_cmdline_core -> free`。
- **根因**：`/usr/lib/libpayload.so` 的命令记录注入逻辑把只读区的回退字符串 `"-"` 当作堆内存释放。它不是项目代码或 Python 依赖错误。
- **解决方案**：所有操作命令保持单行；复杂流程写入 shell 脚本后只执行一条脚本命令；向系统维护者提交最小复现、core stack 和库路径。
- **验证**：单行和脚本文件执行正常；交互式反斜杠续行持续稳定复现崩溃。
- **面试讲法**：强调“逐层缩小故障边界”。先从应用层降到空 Bash，再用 core dump 把问题定位到本机注入库，避免错误地重装深度学习环境。

## 2. Python 环境安装与项目打包连续失败

- **日期**：2026-09-02
- **状态**：已解决。
- **现象**：冻结依赖安装先后遇到 lockfile 与项目名不一致、Hatch 无法自动发现包、PyAV 14.4.0 尝试源码构建并缺少 FFmpeg 开发头文件。
- **根因**：项目被重命名后打包元数据没有同步；源码布局为 `src/openpi`，需要显式配置；当前平台没有 PyAV 14.4.0 的合适安装路径，而 14.2.0 有兼容 wheel。
- **解决方案**：修正项目打包配置，显式指定 `src/openpi`；使用兼容 LeRobot 的 PyAV 14.2.0 wheel；在 `/data` 建立隔离 Python 3.11 环境。
- **验证**：225 个依赖安装完成；Python 3.11.16、JAX 0.5.3、PyTorch 2.7.1、LeRobot 0.3.3 和 PyAV 14.2.0 可导入，选定 CPU 测试通过。
- **面试讲法**：依赖问题需要区分解析、打包和本地编译三个阶段，每个阶段用对应证据处理，不靠反复删除环境碰运气。

## 3. LeRobot 非连续 episode 子集索引错误

- **日期**：2026-09-02
- **状态**：已解决。
- **现象**：训练集和验证集按非连续 episode ID 划分，例如验证集 `(4,14,24)`；上游 LeRobot v0.3.3 的 episode 边界数组是子集相对索引，但查询时仍使用原始 episode ID，可能越界或跨 episode 取动作 chunk。
- **根因**：原始 ID 和子集位置混用。
- **解决方案**：增加本地数据集子类，将原始 episode ID 映射到子集位置后再查询边界；加载时裁剪不需要的大型列。
- **验证**：合成的非连续 episode 边界回归测试确认 action chunk 不跨轨迹；真实验证集长度和末尾 padding 与 Parquet 一致。
- **面试讲法**：强调数据管线中的“ID 语义”。shape 正确不代表样本属于正确轨迹，必须用边界断言测试。

## 4. 训练约 260 步出现 NaN 且没有可恢复 checkpoint

- **日期**：2026-09-03（故障运行开始于 2026-09-02）
- **状态**：根因未定；故障防护已完成。
- **现象**：`real_fr3_4gpu_3000_20260902_203541` 在 step 250 验证 loss 仍有限，step 251 日志正常，约 step 261 的 loss、grad norm 和param norm 同时成为 NaN。首次保存计划在 500 步，因此没有 checkpoint。
- **排查结论**：现有日志不能确定第一个坏 update，也不能证明是数据、梯度、优化器状态、混合精度或硬件导致。原训练循环在 host 检查前已经应用参数更新，发现 NaN 时健康状态可能已被覆盖。
- **解决方案**：在更新前后检查模型、梯度和优化器树；遇到非有限值拒绝该更新，保留更新前健康状态；保存失败 batch、首个坏叶子索引、`numerical_failure.json` 和可恢复 checkpoint，然后立即报错退出。
- **验证**：合成 NaN/Inf 测试确认坏更新不会写入健康状态；后续 3000 步恢复训练记录有限，但不能反推旧故障根因已经消失。
- **面试讲法**：明确区分“增强可观测性与可恢复性”和“证明根因”。没有原始坏 batch 时，不把猜测包装成结论。

## 5. v1 跨 episode 继承旧动作目标

- **日期**：2026-09-03；v3 于 2026-09-09 完成复核。
- **状态**：v3 数据标签已解决；采集端旧缓存的具体代码位置仍需公共采集文件确认。
- **现象**：离线曲线在 episode 开头出现 300～450 mm 动作跳变，真实 state 基本不动。
- **关键证据**：
  - v1 的 29 条轨迹中，28 条首帧 `action-state` 超过 50 mm；
  - 14 条首帧 action 七个维度完全等于上一轨迹的末帧 action；
  - episode 4 前 11 帧保持旧目标，位置差 423.359 mm，机器人 state 相对起点仅变化 0.0053 mm；
  - exporter 只是逐行转换原始 `action.pose7`，说明污染在原始采集 Parquet 中已经存在。
- **根因判断**：高度支持 episode reset 后动作缓存/心跳仍保留上一轨迹目标；缺公共 `record_episode` 源码，无法精确到采集端代码行。
- **解决方案**：v3 将监督明确定义为同一 episode 内 `actions[t] = state[t+1]`，并丢弃每条轨迹最后一个观测，彻底避免旧命令目标作为标签。
- **验证**：逐元素验证全部 29 条轨迹；v3 所有 action 都严格等于 v1 的下一 state。v1 有 527 帧位置差超过 50 mm、最大 456.515 mm；v3 为 0 帧、最大 45.501 mm。
- **面试讲法**：从图像异常回溯到 NPZ、Parquet、原始反馈和转换脚本，逐层证明跳变在哪一层首次出现；修复后用全量逐元素不变量验证，而不是只看几张曲线。

## 6. 轴角在 ±π 附近产生约 2π 数值跳变

- **日期**：2026-09-03 首次发现；2026-09-09 在 v3 全量量化并实现训练修复。
- **状态**：v3 训练路径已解决，等待新模型训练和评估。
- **现象**：连续两帧 rotvec 分量相差约 6.28 rad，看起来像末端旋转一圈；SO(3) 实际旋转通常不到 1°。
- **根因**：轴角表示在 180°附近不唯一。`+πu` 和 `-πu` 表示相同姿态，规范化转换会在分支两侧改变旋转轴符号。旧 `DeltaActions` 直接执行 `action_rotvec - state_rotvec`，把表示切换误当成真实旋转。
- **量化结果**：v3 有 114/6626 个一步标签发生分支切换，最大物理旋转仅 1.225°；旧分量相减却产生约 2π 残差。
- **解决方案**：v3 专用变换使用 `R_relative = inverse(R_state) * R_action`，模型输出后用 `R_action = R_state * R_relative` 恢复绝对姿态。位置仍用相对 XYZ，夹爪保持绝对单指坐标。
- **验证**：正反变换回归和 v3 CPU contract 测试通过；原始 Parquet 可保留轴角分支，因为进入训练前会转换为 SO(3) 最短相对旋转。
- **面试讲法**：不要把欧氏向量差直接用于非欧氏空间。姿态属于 SO(3)，损失和误差都必须尊重群结构。

## 7. 真机动作单位和坐标语义容易重复变换

- **日期**：2026-09-03
- **状态**：已解决并形成接口契约。
- **现象**：采集端包含 VR 增益、坐标映射和控制器目标；容易误以为部署时还要对模型输出再应用相同映射，或者把 7D action 当成七个关节角。
- **根因**：采集控制坐标和训练后策略输出坐标没有书面区分。
- **正确契约**：模型输出是绝对末端 `XYZ(m) + rotvec(rad) + 单指位置(m)`；HTTP `/pose` 使用 `XYZ + XYZW quaternion`；`/move_gripper` 使用总宽度，因此发送 `2 * finger`。策略逆变换已经恢复绝对动作，不能再次加当前 pose 或重复 VR 映射。
- **解决方案**：建立显式输入输出 adapter、shape/finite/unit 检查和 conversion hash；部署代码只做 rotvec→quaternion 与单指→总宽转换。
- **验证**：单位、四元数顺序、夹爪倍数和变换往返测试通过。
- **面试讲法**：机器人部署中最危险的错误常不是模型结构，而是坐标系、单位和“绝对/相对”语义不一致。

## 8. 旧离线测试使用全零触觉样本

- **日期**：2026-09-07
- **状态**：已定位为测试 fixture 问题；不代表真机或 checkpoint 不兼容。
- **现象**：分支专用部署测试 34 项通过，扩展测试 53 项通过、2 项失败。失败样本把 `[9,198,2]` 触觉坐标全部写成零。
- **根因**：真实触觉 contract 的第 0 帧必须是固定左右参考网格，后八帧是当前 marker 坐标。全零数组不是“无触觉”或“零剪切”，而是非法几何输入，被严格校验正确拒绝。
- **解决方案**：测试需要构造固定参考网格，或在明确测试无触觉模型时完全移除触觉分支；不能用全零坐标冒充无接触。
- **验证**：真机完整 shadow 日志中的左右触觉为有限、非零且 shape 正确。
- **面试讲法**：失败的测试不一定说明生产代码错，也可能说明 fixture 已落后于接口语义。判断标准是生产 contract，而不是让测试无条件变绿。

## 9. 触觉与 RGB 基线不是严格单变量对照

- **日期**：2026-09-07
- **状态**：已识别，严格实验仍待运行。
- **现象**：触觉模型和 RGB+state 模型的离线结果接近，部分指标反而无触觉更好，但两次运行初始化不同。
- **根因**：触觉模型从本地 tactile smoke 99 warm-start，RGB 模型从 published Tabero 49999 开始，不能把差异只归因于触觉模态。
- **解决方案**：固定数据划分、初始化、训练步数、随机种子、归一化、离线 anchor 和采样噪声，只改变触觉输入/分支；按 episode、接触阶段和任务成功率报告。
- **验证结论**：现有证据不能证明触觉有效，也不能证明触觉无用。离线逐帧误差也不能替代真机任务成功率。
- **面试讲法**：机器学习实验必须控制变量。看到指标差异先审计实验配对关系，再讨论模型结论。

## 10. 最低验证 loss 不等于最佳物理动作指标

- **日期**：2026-09-07
- **状态**：模型选择方法已修正。
- **现象**：new-prompt tactile checkpoint 2000 的验证 loss 最低，但与 2999 做相同离线评估后，只在部分旋转长尾上更好，位置、夹爪和完整 chunk 指标更差。
- **根因**：flow-matching validation loss 是归一化训练目标，不等同于毫米、角度、夹爪越界率或任务成功率；不同 checkpoint 的误差分布也可能发生权衡。
- **解决方案**：checkpoint 选择同时看配对物理指标、P95/P99/max、安全越界率、分 episode 结果和最终真机成功率，不只看单一平均 loss。
- **验证**：2000 与 2999 使用相同 693 anchors、seed、noise、horizon、norm hash 和数据 hash 做成对比较。
- **面试讲法**：把优化目标、离线代理指标和最终业务指标分层，说明为什么三者可能不一致。

## 11. 触觉桥未启动导致 `stopped: "'left'"`

- **日期**：2026-09-08
- **状态**：已解决。
- **现象**：程序完成 server metadata 校验后立即退出，reason 为 `"'left'"`。
- **排查过程**：错误形态是访问 `frames['left']` 的 KeyError，而不是模型推理、shape 或 WebSocket 错误。用户确认当时触觉桥没有启动；随后完整 shadow 中左右触觉持续正常。
- **根因**：启动依赖缺失，程序尚未收到左触觉首帧。
- **解决方案**：按顺序启动触觉桥并检查 ROS topic；启动等待错误改为列出所有缺失流，而不是裸 KeyError。
- **验证**：后续 30 秒日志有 149 个有效触觉 chunk，左右统计均有限且非零。
- **面试讲法**：从异常类型和生命周期阶段判断问题层次，避免一看到“触觉”就怀疑模型或驱动数据格式。

## 12. checkpoint、norm stats 与 conversion 可能配错

- **日期**：2026-09-08
- **状态**：本次事故已排除；运行时校验已加入。
- **现象**：真机输出幅度异常，首先需要排除 checkpoint 使用了错误归一化统计、动作单位或转换配置。
- **风险原理**：模型学习的是归一化动作。错误的 q01/q99、mean/std 或错误的绝对/相对语义，会在反归一化后直接放大成真实空间跳变。
- **排查方法**：server 返回 config、checkpoint、action horizon、dataset fps、use_tactile、`norm_stats_sha256` 和 `conversion_sha256`；客户端连接时严格比对并写入日志。
- **结论**：当次 checkpoint 2000 的 norm hash 与本机两个对应 checkpoint 资产完全一致，conversion hash 也一致，因此“文件复制错了”被排除。它不能证明训练数据本身正确。
- **面试讲法**：用内容哈希和 provenance 把配置问题变成可证伪问题，不通过文件名或路径猜版本。

## 13. Shadow 中异步索引放大动作与当前状态距离

- **日期**：2026-09-08
- **状态**：机制已定位；需要在新模型和实际跟随条件下重新验证。
- **现象**：推理约 240～265 ms 后返回，控制器按时间选择 `action[2]` 或 `action[3]`；这些动作与当前 state 的距离明显大于 `action[0]`。
- **根因**：模型根据旧观测预测未来轨迹；正常执行时机器人应同时执行前序动作。Shadow 模式不移动机器人，因此未来动作与静止 state 的距离必然增长。推理延迟、限速导致的跟随落后和索引误差会进一步放大。
- **关键证据**：完整 30 秒日志中，action0/state 位置距离 p50 23.18 mm、p95 61.35 mm、max 142.86 mm；选中 action2/3 后为 p50 43.93 mm、p95 90.53 mm、max 377.38 mm。机器人 current 与 observation 的中位差只有 0.0021 mm。

## 26. 长时同步 execute 因 ZED 前视帧延迟触发传感器 skew 停止

- **日期**：2026-09-09。
- **状态**：客户端按设计停止并发送保持位姿命令；ZED 前视帧短时延迟的上游根因尚未定位，230秒长时执行未完成。
- **现象**：`sync_execute_004`请求执行230秒，但约8秒、控制台报告40次同步推理后退出。异常为`Sensor capture timestamps are not synchronized: skew=0.117s`，随后出现Python traceback。
- **证据**：停止瞬间前视`front`帧年龄144.877 ms，腕部图像30.834 ms、机器人状态27.783 ms、左右触觉57.373/58.736 ms；因此最老的前视帧和最新状态相差117.094 ms，超过`max_sensor_skew_sec=100 ms`，但各流自身仍低于250 ms年龄上限。控制台明确记录`Sent best-effort measured-pose hold`。所附JSONL因粘贴截断只有39个完整tick及第40个残缺chunk；39个完整tick全部`ok=true`并发送pose，28个发送gripper。推理延迟均值198.27 ms、结果年龄最大304.10 ms；35/39次触发平移速率限幅、3次触发旋转速率限幅，没有workspace越界。上一命令到当前实测的跟踪误差最大4.06 mm和0.60°，远低于30 mm和11.46°停止阈值。机械臂在完整记录内累计移动约`[+14.26,+3.09,-11.51] mm`、旋转1.29°、夹爪总宽收紧1.87 mm。
- **根因或假设**：直接触发条件已确定为前视帧相对其他输入延迟，不是模型目标越界、机器人跟踪误差或启动时DDS type-hash警告。前视相机发布抖动、ROS/DDS传输短时丢帧或重传、以及客户端图像解码/线程调度延迟都是候选原因；当前没有同一时段的topic频率和delay序列，不能确定上游根因。起始状态仍存在明显训练分布偏移，但它与本次传感器skew停止是两个独立问题。
- **解决方案**：当前fail-closed行为保留：不使用时间错位观测继续推理，退出时发送一次实测位姿hold。部署主机需先拉取提交`78c8d5c`，以后异常会在JSONL明确写`stopped`事件；本次metadata缺少`asset_id`且行号仍对应旧代码，说明该主机尚未更新。复测前分别对ZED前视topic运行`ros2 topic hz`、`ros2 topic delay`和`ros2 topic info --verbose`，确认发布频率、延迟尾部和QoS；先不要直接把100 ms阈值调大。若确认只是单帧偶发延迟，再设计“保持上一目标并等待下一组有效同步样本”的有界恢复机制，并在shadow验证后用于真机。
- **验证范围**：已从终端确认停止原因和hold请求，从附件39个完整tick确认停止前限速、跟踪与HTTP发送正常；没有硬件急停状态、完整原始JSONL尾部、ZED同时间段频率/延迟统计或现场任务结果，因此不能声称相机根因已修复或任务成功。
- **面试讲法**：多模态真机控制既要检查每路数据是否新鲜，也要检查它们是否描述同一时刻。这里所有传感器都没有单独过期，但前视图像比机器人状态慢117 ms；客户端拒绝这组错位观测并保持当前位姿，从而把感知时序故障隔离在动作发送之前。随后用每个topic的频率、延迟和QoS定位上游，而不是先放宽安全阈值。

## 当前推荐的端到端排查顺序

1. **验证数据不变量**：episode 边界、`actions[t]` 语义、时间戳、单位、shape、finite、视频/触觉同步。
2. **验证动作几何**：位置使用米，姿态用 SO(3) 相对旋转，夹爪区分单指和总宽。
3. **绑定模型资产**：checkpoint、config、norm stats、conversion 和 prompt 全部记录哈希与 provenance。
4. **离线成对评估**：固定 anchors、noise、seed、horizon、split，报告毫米、角度、P95/P99/max 和越界率。
5. **Shadow 分层记录**：完整 chunk、action0、action[k]、当前 state、观测年龄、传感器时间和 chunk 切换。
6. **检查分布偏移**：相机视角、TCP、起始六自由度姿态、触觉参考网格和任务文本。
7. **最后才做真机执行**：持续使能、workspace、target jump、tracking error、rate limit、底层 watchdog 和硬件停止全部有效。

## 面试回答模板

可以按下面六句话组织每个案例：

1. **场景和影响**：系统处在哪一阶段，问题阻塞了什么。
2. **可复现现象**：给出最小复现和关键数字。
3. **最初假设**：列出两到三个候选原因，不提前下结论。
4. **证据链**：说明如何逐层排除，并指出决定性证据。
5. **修复和保护措施**：既修根因，也增加断言、日志、哈希或 fail-closed 防护。
6. **验证边界**：说明什么已经被测试，什么还需要训练或真机实验。
